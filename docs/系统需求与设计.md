# AI 会谈辅助系统需求与设计

## 1. 文档说明

本文档为 AI 会谈辅助系统第一版需求与设计文档，用于明确系统目标、核心功能、技术路线、模块划分、数据结构与后续开发计划。

系统定位为：

> 一个运行在客户本地笔记本电脑上的 AI 会谈辅助系统，用于在客户会谈、需求沟通、销售交流等场景中实时记录语音、转换文字、识别说话人，并根据预设会晤目标生成合适的应答建议。

---

## 2. 项目背景

在客户沟通、需求调研、售前交流等场景中，沟通过程通常存在以下问题：

1. 会谈内容难以及时完整记录；
2. 需求表达口语化、碎片化，后续整理成本高；
3. 客户提出异议时，沟通人员需要快速组织专业答复；
4. 新员工缺少经验，容易遗漏关键信息或回应不当；
5. 会后纪要、行动项、客户关注点需要人工整理；
6. 涉及客户信息时，不适合将完整录音和转写内容上传到集中服务器。

因此，本系统采用本地部署方式，在客户或使用者自己的笔记本电脑上运行全部核心组件，尽量保证数据本地化，同时通过第三方大模型 API 提供智能建议能力。

---

## 3. 系统目标

### 3.1 总体目标

构建一个本地运行的 AI 会谈辅助系统，实现从语音记录、语音转文字、说话人识别、角色区分，到 AI 建议回复和会话文件保存的完整流程。

### 3.2 核心目标

1. 支持在本地浏览器页面中发起会谈记录；
2. 支持输入本次会晤目标；
3. 支持本地录音并进行语音转文字；
4. 使用本地 FunASR streaming 完成实时语音识别，faster-whisper 保留为短音频 fallback，并可开启双语识别增强处理中英文混合 final 音频；
5. 使用 SpeechBrain ECAPA 完成声纹识别和未知说话人聚类；
6. 前端按语音停顿 0.8s 进行端点切分，服务端对过长 final 音频按静音/最大时长做兜底切分；
7. 支持会前录入参会人声纹；
8. 支持在会谈过程中识别发言人；
9. 支持配置哪些参会人的发言需要 AI 生成答复建议；
10. 支持客户发言显示为白色文字，我方发言显示为黄色文字；
11. 支持根据会晤目标、历史会话和客户最新发言生成建议回复；
12. 支持完整会话记录保存和导出。

## 5. 部署模式

### 5.1 部署原则

系统采用单机本地部署模式。

每个使用者从 GitHub 拉取项目文件，在自己的笔记本电脑上运行完整系统。系统可以划分为 `server` 和 `client` 两个组件，但二者均运行在本机。

### 5.2 推荐部署方式

推荐使用 Docker Compose 部署。

示例启动方式：

```bash
git clone <repository-url>
cd ai-meeting-assistant
cp .env.example .env
docker compose up -d
```

启动后访问：

```text
http://localhost:3000
```

### 5.3 本地数据保存

系统运行过程中产生的数据保存在本地 `data/` 目录中。

```text
data/
├── participants/        # 参会人配置与声纹数据
├── sessions/            # 会话 JSON 记录
├── audio/               # 原始录音或语音片段
├── transcripts/         # 转写文本
└── exports/             # 导出的 Markdown/TXT 文件
```

模型缓存建议挂载到本地目录：

```text
model_cache/             # 旧 ModelScope 缓存目录；当前不再作为模型源使用，可保持为空
hf_cache/                # HuggingFace 缓存；FunASR streaming、ct-punc、faster-whisper、ECAPA、cam++ diarization
```

### 6.3 语音识别与 ASR 选型

#### 6.3.1 第一阶段：faster-whisper 短音频块识别

项目第一阶段语音识别采用：

```text
faster-whisper
```

推荐模型：

| 使用场景 | 推荐模型 |
|---|---|
| 普通笔记本演示 | small |
| 速度优先 | base / small |
| 准确率优先 | medium |
| GPU 环境 | medium / large-v3 |

第一版建议默认使用：

```text
faster-whisper small
```

该方案优点是接入简单、生态成熟、可本地运行，并且能复用 Whisper 系列模型。但在实际会议场景中发现以下问题：

1. 它不是原生流式 ASR，更适合“短音频文件识别”；
2. 浏览器端如果使用 `MediaRecorder` 生成音频块，会出现识别延迟；
3. 若环境底噪导致前端 VAD 不稳定，容易表现为“停止录音后才识别”；
4. CPU 环境下 `small` 模型准确率和实时性都有限；
5. 中文会议中存在口语、专有名词、多人打断、ASR 断句等问题，Whisper 短块识别效果不稳定。

因此，faster-whisper 保留为 fallback 和离线短音频识别方案，但不再作为实时字幕能力的唯一实现。

#### 6.3.2 ASR 方案对比

针对“中文多人会议实时字幕/实时会话”场景，对以下方案进行比较：

| 方案 | 实时性能 | 中文会议准确率 | 部署复杂度 | 备注 |
|---|---:|---:|---:|---|
| Whisper Streaming | 中 | 中高 | 中 | 基于 Whisper 滑动窗口模拟流式，非官方原生流式 |
| faster-whisper streaming wrapper | 中 | 中高 | 低~中 | 与现有 faster-whisper 兼容，改造成本低，但仍是准流式 |
| sherpa-onnx | 高 | 中~中高 | 中 | 本地低延迟能力强，模型选择和中文效果需实测 |
| FunASR streaming | 高 | 高 | 中 | 更适合中文会议，支持流式识别，适合当前场景 |
| Vosk | 高 | 中低 | 低 | 实时性好，但准确率通常不满足销售会议需求 |
| NVIDIA Riva | 很高 | 高 | 高 | 企业级 GPU 方案，部署成本高 |

综合考虑本项目当前目标：

- 中文销售会议；
- 本地或私有化部署；
- 希望接近实时字幕体验；
- 不强制依赖 NVIDIA GPU；
- 需要比 faster-whisper 文件块识别更低延迟；

最终选择：

```text
FunASR streaming
```

#### 6.3.3 当前 FunASR streaming 落地方式

当前实现采用 WebSocket 音频流方式：

```text
浏览器麦克风
→ WebAudio 采集 PCM
→ 下采样为 16kHz PCM16
→ WebSocket 持续推送音频帧
→ FastAPI WebSocket 接口
→ FunASR streaming 返回 partial 文本
→ 语音段结束后返回 final Message
→ 写入实时会话
```

对应后端接口：

```text
WebSocket /api/meetings/{meeting_id}/asr/funasr/stream
```

返回类型：

```json
{ "type": "partial", "text": "临时字幕" }
```

```json
{ "type": "final", "message": { "text": "最终识别文本" } }
```

前端保留 `0.8s` 语音间断切分逻辑，用于向服务端发送 final 控制帧；同时服务端使用 FunASR streaming 做实时识别。

#### 6.3.4 与声纹识别的配合

FunASR 负责实时语音转文字；SpeechBrain 仍负责说话人识别。

由于声纹识别不适合逐帧实时执行，当前策略为：

1. 前端持续推送 PCM 流；
2. FunASR 实时返回 partial；
3. 当前语音段 final 后，服务端保存该段 wav；
4. 对 final 语音段执行 SpeechBrain 声纹识别；
5. 将识别文本、说话人、声纹分数一并返回实时会话。

这样可以兼顾实时字幕体验和说话人识别成本。

#### 6.3.5 与 FunASR / SpeechBrain 最佳实践对齐

当前实现已按官方最佳实践修正以下问题：

1. **chunk 对齐**：`chunk_size=[0,10,5]` 要求每次 `generate` 输入 `10 * 960 = 9600 samples`（16kHz 下 600ms），服务端按 600ms 组块；之前 1200ms 会破坏 decoder lookback 约定，导致识别碎、语义不连贯；
2. **流式状态隔离**：每个语义段 final 后清空 `FunASRStreamingSession.cache`，避免前一段的 encoder/decoder 缓存污染下一段；
3. **并发保护**：共享的 FunASR 模型通过线程锁串行化 `generate` 调用；ASR 与声纹推理均通过 `asyncio.to_thread` 放到线程池，避免阻塞 WebSocket 事件循环；
4. **声纹阈值分层**：`speaker_threshold=0.30` 用于匹配已知参会人；`speaker_cluster_threshold=0.45` 用于合并未知说话人的多段语音。后者越低越容易把同一人的片段合并，越高越容易拆成多个 `voice_xxx`；
5. **模型缓存**：FunASR streaming、final 标点 `ct-punc`、SpeechBrain ECAPA 和可选 cam++ diarization 均使用 HuggingFace 缓存；SpeechBrain `EncoderClassifier` 固定 `savedir` 到已挂载的 `hf_cache/`，避免重复下载和 HuggingFace 校验错误；
6. **embedding 归一化**：ECAPA embedding 做 L2 归一化后存储，相似度计算更稳定，并兼容旧的未归一化文件；
7. **短音频降级**：短于 `3.0s` 的语音段不做声纹识别/聚类，复用当前会议最近的 unknown speaker，避免不可靠 embedding 造成误匹配或过度拆分；
8. **长音频兜底切分**：服务端对超过约 10 秒的 final 音频按静音/最大时长切成更适合声纹识别的小段，降低一条长音频混入多人发言的概率；
9. **cam++ 可选增强**：FunASR `cam++` / `campplus` 说话人分离默认关闭，可在前端设置中开启。当前实现通过 `hub="hf"` 强制使用 HuggingFace 模型源（映射到 `funasr/paraformer-zh`、`funasr/fsmn-vad`、`funasr/campplus`），避免部分网络环境下 ModelScope 大文件下载/合并失败；该链路首次触发仍会下载较大模型，建议 Colima 分配约 12GB 内存后再开启。

#### 6.3.6 后续优化方向

1. 优化标点恢复模型效果与延迟；
2. 增加热词/客户名/产品名词典；
3. 支持 partial 字幕单独显示，final 后写入正式会话；
4. 针对多人重叠发言优化 `cam++` diarization 与 ECAPA 跨段聚类协同；
5. 根据部署环境选择 CPU/GPU 模型；
6. 保留 faster-whisper HTTP 短块识别作为 fallback。

### 6.4 声纹识别

声纹识别采用：

```text
SpeechBrain
```

用途：

- 录入参会人声音样本；
- 提取参会人声纹向量；
- 对会议语音片段进行声纹匹配；
- 判断当前发言人。

当前实现将说话人识别分为两层：

- 已知参会人匹配：使用 `speaker_threshold` 与已录入声纹样本比较；
- 未知说话人聚类：使用 `speaker_cluster_threshold` 将未绑定的多段发言合并成稳定的 `voice_xxx`。

如果同一个人被拆成多个 `voice_xxx`，应降低 `speaker_cluster_threshold`；如果不同人被合并，应提高该值。ASR 和说话人归属都存在不确定性，前端仍保留手动绑定/修正流程。

### 6.5 语音切分

当前采用“前端端点检测 + 服务端兜底切分”的方式。

基本思路：

1. 前端持续采集音频并计算音量能量；
2. 当音量高于 `energy_threshold` 时判断为有人说话；
3. 当音量持续低于阈值并超过 `silence_duration_ms` 时判断为一段 final 语音结束；
4. 前端将 final 音频发送给后端做 ASR 和声纹识别；
5. 如果 final 音频过长，服务端再按静音/最大时长做二次切分，降低单段混入多位说话人的概率。

第一版不追求完全解决多人重叠语音，优先保证普通销售会谈场景下的流程可用。遇到句内多人快速交替或重叠说话，可选择开启 `cam++` 说话人分离，但仍应允许人工修正。

### 6.6 大模型调用

大模型采用第三方 API 方式，不在本地运行大模型。

系统应借鉴 OpenCode 的模型配置思路，支持多 Provider、多模型、可配置 API Key 和 Base URL。

示例配置：

```env
LLM_PROVIDER=deepseek
LLM_MODEL=deepseek-chat
LLM_API_KEY=your_api_key
LLM_BASE_URL=https://api.deepseek.com
```

后续可扩展支持：

- DeepSeek；
- OpenAI；
- 通义千问；
- 智谱；
- Moonshot；
- 其他 OpenAI Compatible API。

## 8. 核心业务流程

### 8.1 会前配置流程

```text
打开系统
  ↓
创建或选择会谈
  ↓
输入会晤目标
  ↓
维护参会人列表
  ↓
录入参会人声纹样本
  ↓
设置参会人角色和是否需要 AI 答复
  ↓
开始会谈
```

### 8.2 会中辅助流程

```text
浏览器采集语音
  ↓
前端按 0.8s 语音停顿切分语义段并流式推送
  ↓
FunASR streaming 实时转写文字
  ↓
SpeechBrain 识别发言人
  ↓
前端展示发言内容（实时会话区）
  ↓
本地规则分析：打标签并判断是否为问题/明确请求
  ↓
说明/示例/解释 → 仅写入结构化上下文（不触发回复）
问题/明确请求   → 进入下一步
  ↓
判断该发言人是否为指定参会人（need_reply）
  ↓
两者都满足则调用远程大模型生成建议回复，并注入结构化上下文
  ↓
前端 AI Q&A 区展示建议回复
```

### 8.3 会后保存流程

```text
结束会谈
  ↓
保存完整会话 JSON
  ↓
生成转写文本
  ↓
生成 Markdown/TXT 导出文件
  ↓
可选生成会议总结和待办事项
```

## 9. 功能需求

### 9.1 会晤目标管理

用户可以在会谈开始前输入本次会晤目标。

示例：

```text
了解客户当前业务流程痛点，确认是否需要进一步安排需求调研会议。
```

会晤目标用于约束 AI 建议回复的方向。

### 9.2 参会人管理

系统支持维护参会人列表。

每个参会人包含：

- 姓名；
- 角色；
- 声纹样本；
- 是否需要 AI 答复；
- 展示颜色；
- 备注。

角色建议包括：

- 我方；
- 客户；
- 其他。

### 9.3 声纹录入

用户可以为每个参会人录入声音样本。

建议录入要求：

- 每人录音 20 至 60 秒；
- 尽量在安静环境下录制；
- 使用正式会谈时相同或相近的麦克风；
- 录音内容可为任意自然讲话。

系统根据录音生成声纹向量，并保存在本地。

### 9.4 语音转文字

系统有两条转写路径，由运行配置中的 `asr_provider` 决定（详见第 6.3 节）：

- **实时字幕**（WebSocket `/asr/funasr/stream`）：固定使用本地 FunASR streaming，前端按 0.8s 语音停顿发送 final 控制帧；
- **短音频上传**（HTTP `/audio`）：按 `asr_provider` 分派——`funasr_streaming`（默认，整段识别）、`faster_whisper`（分段带时间戳）、`oci_speech`（尚未接入，返回 501）。

当 `bilingual_asr_enabled=true` 时，系统会在 final 音频阶段优先使用 faster-whisper 自动语言识别增强中英文混合转写；如果 faster-whisper 模型不可用或识别失败，则回退到 FunASR streaming 结果。该增强默认关闭，避免在网络或模型缓存不稳定时引入额外下载和延迟。

ASR final 文本入库前会按 `punctuation_provider` 选择标点策略。实时 FunASR streaming 原始 final 通常不带标点，因此默认使用 HuggingFace `funasr/ct-punc` 进行中文标点恢复；也可以切换为 `asr`（信任 ASR/Whisper 原始标点）、`rule`（本地轻量规则）或 `off`（关闭）：

- partial 实时字幕最多做轻量规则补标点，保证低延迟；
- final 文本默认走 `funasr_punc`，前端不再二次补标点；
- 规则标点和 partial 显示使用固定保守规则，不再提供敏感度参数；
- 已有标点不重复插入。

该步骤不依赖本地 LLM，主要用于改善“实时会话”区域可读性。

> 模型源状态：FunASR streaming、独立 final 标点服务、SpeechBrain ECAPA 和 cam++ diarization 的 active 模型源均已统一为 HuggingFace；历史 ModelScope 缓存可清理。

转写结果包含：

- 文本内容；
- 开始时间；
- 结束时间；
- 识别语言；
- 置信度，若模型支持。

### 9.5 说话人识别

系统使用 SpeechBrain 对语音片段进行声纹识别。

识别流程：

1. 提取当前语音片段的 speaker embedding；
2. 与本地参会人声纹库进行相似度计算；
3. 选择相似度最高的参会人；
4. 如果相似度低于已知参会人阈值，则进入未知说话人聚类；
5. 未知说话人按聚类阈值复用或创建 `voice_xxx`；
6. 前端允许用户手动绑定/修正说话人。

### 9.6 会话展示

前端页面实时展示会话记录。

展示规则：

- 客户发言：白色文字；
- 我方发言：黄色文字；
- 未知说话人：灰色文字；
- AI 建议回复：独立区域展示。

示例：

```text
客户-李四：我们比较担心上线周期太长。

我方-张三：这个问题可以理解，我们可以分阶段推进。

AI建议：建议先共情客户对周期的担忧，再说明可通过分阶段实施降低风险。
```

### 9.7 AI 建议回复

当发言人被标记为“需要 AI 答复”，且本地分析判定发言为“问题/明确请求”时，系统调用大模型生成建议回复。

判断条件（两者需同时满足）：

- 参会人配置中 `need_reply = true`（指定参会人）；且
- 本地会话分析 `UtteranceAnalysis.should_reply = true`。

#### 本地会话分析与回复过滤

实时会话中的 ASR 文字包含大量说明、示例、解释等描述性内容，这类内容不需要 AI 答复，但应作为后续回复与总结的上下文参考。因此采用“本地规则分析 + 远程 LLM”的两层方案，**本地不运行 LLM**：

1. **本地规则分析**（`context_manager.analyze_utterance()`）
   - 对每条 final 文本打标签：`question`、`context_note`、`key_fact`、`pain_point`、`risk`、`commitment`、`todo`；
   - 强问题信号（问号、`吗`、`能否`、`是否`、`能不能` 等）直接判为问题；弱信号（`什么`、`怎么`、`如何` 等）在没有说明性标记时才判为问题；
   - 说明/示例/解释（含 `比如`、`例如`、`我们的流程是`、`我说明一下` 等）判为 `context_note`，`should_reply=false`；
   - `没什么问题/没问题` 等否定表达抑制误判；疑问句中的“提供/安排”不记为我方承诺；
   - 计算 `importance` 并给出可读的 `reason`，随消息保存便于追溯。

2. **只处理 final 文本**
   - partial 仅供实时字幕显示，不进入分析与记忆；
   - 每个语义段 final 后才做一次分析、更新记忆与触发判断。

3. **上下文归纳**（结构化记忆）
   - 说明性内容写入 `AgentMemory.context_notes`，明确事实写入 `key_facts`；
   - 痛点、风险、承诺、待办、问题继续写入对应列表，各列表有上限（30 条）；
   - `format_context_for_llm()` 将结构化记忆拼成提示词片段，并显式标注“背景说明（非问题，仅供参考）”。

4. **远程 LLM 调用**
   - 仅在 `should_trigger_reply(need_reply, analysis)` 为真时调用 `suggest_reply()`；
   - 建议回复与会后总结的提示词均注入结构化上下文；
   - 人工把某条消息修正为“需要答复”属于显式意图，直接生成回复，但仍带上结构化上下文。

生成依据：

- 本次会晤目标；
- 本地归纳的结构化上下文（事实/背景/痛点/风险/承诺/待办/问题）；
- 最近若干轮会话记录；
- 客户最新发言。

### 9.8 手动修正

由于声纹识别可能存在误判，系统必须支持手动修正。

用户可以：

保存内容包括：

### 9.10 文件导出

第一版支持：

后续可扩展支持：

## 18. 风险与注意事项

### 18.1 声纹识别准确率风险

声纹识别受录音环境、麦克风距离、背景噪音、说话时长影响较大，因此必须保留人工修正功能。

### 18.2 实时性风险

FunASR streaming、faster-whisper（fallback）和 SpeechBrain 在普通 CPU 笔记本上可能存在一定延迟。第一版应优先保证可用性，而不是追求完全实时。

### 18.3 隐私风险

虽然音频和转写在本地处理，但调用第三方大模型 API 时，会发送部分会话文本。系统应明确提示用户，并支持控制发送内容范围。

### 18.4 大模型幻觉风险

AI 建议仅作为辅助，不应作为最终承诺。提示词中应约束模型不要编造产品能力、价格、交付周期等信息。

## 19. 第一版结论

本系统第一版采用以下技术路线：

```text
本地部署：Docker Compose
前端：React + Vite + TypeScript
后端：Python + FastAPI
语音识别：FunASR streaming（实时）/ faster-whisper（短音频 fallback）
声纹识别：SpeechBrain
语音切分：前端语音停顿 0.8s（服务端无 VAD）
大模型：第三方 API，可配置 Provider / Model / Base URL / API Key（Key 对外掩码显示）
存储：本地文件系统
```

该方案具备以下特点：

1. 适合单机本地部署；
2. 音频和声纹数据保存在本地；
3. 技术复杂度适中；
4. 适合公司 AI 技能大赛演示；
5. 后续具备扩展为正式产品的空间。
